# FUNCTIONAL SPECIFICATION
# Telegram Dispatcher Platform

Этот документ описывает функциональные требования к системе.

---

## Stage 2.1 — Авторизация диспетчера через QR (Telethon)

### Описание
Диспетчер авторизуется в системе через QR-код, используя Telethon для создания пользовательской сессии Telegram.

### Функциональные требования

1. **Инициация авторизации**
   - Диспетчер запускает процесс авторизации через бота
   - Бот генерирует QR-код для сканирования
   - QR-код содержит временный токен авторизации

2. **Процесс авторизации**
   - Диспетчер сканирует QR-код через приложение Telegram
   - Telethon создает пользовательскую сессию
   - Сессия шифруется и сохраняется локально
   - После успешной авторизации диспетчер получает доступ к системе

3. **Управление сессией**
   - Одна сессия = один диспетчер
   - Сессия мониторится на активность
   - Истекшая сессия блокирует отправку заказов
   - Диспетчер может переавторизоваться при необходимости

4. **Безопасность**
   - Сессии хранятся в зашифрованном виде
   - Проверка валидности сессии перед каждым действием
   - Автоматическое отключение при подозрительной активности

## Stage 2.2 — Жизненный цикл заказа (FSM)

### Описание
Заказ проходит через строго определенные состояния конечного автомата (FSM).

### Состояния FSM

1. **draft** (черновик)
   - Заказ создан, но не готов к отправке
   - Можно редактировать все поля
   - Не виден водителям

2. **preview** (предпросмотр)
   - Заказ нормализован и готов к просмотру
   - Показывается диспетчеру для проверки
   - Можно вернуться к редактированию (draft)

3. **confirmed** (подтвержден)
   - Диспетчер подтвердил заказ
   - Готов к отправке в группы
   - Нельзя вернуться к draft/preview

4. **sending** (отправка)
   - Заказ находится в процессе отправки в группы
   - Применяется Anti-Ban логика
   - Можно отменить отправку (→ cancelled)

5. **active** (активен)
   - Заказ отправлен во все выбранные группы
   - Ожидает ответов от водителей
   - Можно редактировать, отменять, назначать водителя

6. **assigned** (назначен)
   - Водитель назначен на заказ
   - Заказ больше не принимает новые ответы
   - Можно закрыть (→ closed) или сменить водителя

7. **closed** (закрыт) — КОНЕЧНОЕ
   - Заказ выполнен
   - Нельзя изменить состояние
   - История сохраняется

8. **cancelled** (отменен) — КОНЕЧНОЕ
   - Заказ отменен диспетчером
   - Нельзя изменить состояние
   - История сохраняется

### Переходы между состояниями

```
draft → preview → confirmed → sending → active → assigned → closed
                                    ↓
                                cancelled
```

### Правила переходов
- `closed` и `cancelled` — конечные состояния, возврат невозможен
- Все переходы логируются
- Критические переходы требуют подтверждения

## Stage 2.3 — Сценарии отправки

### Описание
Диспетчер может отправлять заказы по различным сценариям.

### Типы сценариев

1. **Сохраненные сценарии**
   - Диспетчер создает именованные сценарии
   - Сценарий = набор групп + параметры отправки
   - Можно выбрать готовый сценарий при отправке

2. **По региону**
   - Выбор региона из списка
   - Автоматический выбор всех групп региона
   - Можно добавить дополнительные группы

3. **Все группы**
   - Отправка во все группы диспетчера
   - С предупреждением о количестве групп
   - Требует подтверждения

4. **Ручной выбор**
   - Диспетчер выбирает группы вручную
   - Показывается список всех доступных групп
   - Можно выбрать несколько групп

### Информация перед отправкой

Перед отправкой диспетчеру показывается:
- **Список групп** — куда будет отправлен заказ
- **Текст заказа** — финальная версия
- **Задержки** — расчетное время отправки с учетом Anti-Ban
- **VIP приоритет** — если заказ VIP, показывается отдельно
- **Индикатор риска** — оценка риска блокировки аккаунта

### Подтверждение отправки
- Всегда требуется явное подтверждение
- Без подтверждения заказ не отправляется
- После подтверждения начинается процесс отправки

## Stage 2.4 — Обработка ответов водителей

### Описание
Система отслеживает ответы водителей в группах и сохраняет их.

### Типы ответов

1. **"я"**
   - Точное совпадение слова "я" (регистронезависимо)
   - Может быть частью предложения
   - Учитывается как ответ на заказ

2. **Reply на заказ**
   - Любой ответ (reply) на сообщение с заказом
   - Неважно, что написано в ответе
   - Главное — факт reply на сообщение заказа

### Сохраняемые данные

Для каждого ответа сохраняется:
- **Текст** — полный текст ответа
- **Ник** — @username водителя (если есть)
- **Имя** — отображаемое имя
- **ID** — Telegram user ID
- **Группа** — в какой группе был ответ
- **Время** — точное время ответа
- **Телефон** — номер телефона (если доступен в профиле)

### Обработка дубликатов
- Один водитель может ответить несколько раз
- Все ответы сохраняются
- При назначении показываются все ответы водителя

### Мониторинг
- Система постоянно мониторит группы с активными заказами
- Новые ответы обрабатываются в реальном времени
- Диспетчер получает уведомления о новых ответах

## Stage 2.5 — Логика назначения водителя

### Описание
Диспетчер назначает водителя на заказ вручную из списка откликнувшихся.

### Правила назначения

1. **Только вручную**
   - Автоматическое назначение запрещено
   - Только диспетчер может назначить водителя

2. **Только из откликнувшихся**
   - Можно назначить только того, кто ответил на заказ
   - Нельзя назначить водителя, который не откликнулся

3. **Всегда с подтверждением**
   - Перед назначением показывается подтверждение
   - Показывается информация о водителе и заказе
   - Без подтверждения назначение не происходит

### Процесс назначения

1. Диспетчер видит список всех откликнувшихся водителей
2. Выбирает водителя из списка
3. Система показывает информацию о водителе и заказе
4. Диспетчер подтверждает назначение
5. Система отправляет reply в группу: "✅ Отдан Вам"
6. Заказ переходит в состояние `assigned`
7. Новые ответы больше не принимаются

### Смена назначенного водителя

**Разрешена, но строго по правилам:**

1. Можно сменить только на другого откликнувшегося водителя
2. Обязательно указать причину смены
3. История назначений неизменяема (все назначения сохраняются)
4. В группе отправляется новое сообщение о назначении
5. Предыдущий водитель уведомляется (опционально)

## Stage 2.6 — Редактирование/отмена/закрытие заказов

### Описание
Три разных действия с заказами, каждое имеет свой смысл и правила.

### Редактирование заказа

**Когда:** Заказ в состоянии `active` или `assigned`

**Что происходит:**
- Меняются условия заказа (текст, параметры)
- Все сообщения в группах обновляются
- История изменений сохраняется
- Требуется подтверждение

**Процесс:**
1. Диспетчер редактирует заказ
2. Показывается preview изменений
3. Подтверждение редактирования
4. Система обновляет ВСЕ сообщения в группах
5. Водители видят обновленный заказ

### Отмена заказа

**Когда:** Заказ в состоянии `draft`, `preview`, `confirmed`, `sending`, `active`, `assigned`

**Что происходит:**
- Заказ переходит в состояние `cancelled`
- Все сообщения в группах обновляются (помечаются как отмененные)
- История сохраняется
- Требуется подтверждение

**Процесс:**
1. Диспетчер выбирает отмену
2. Указывает причину отмены (опционально)
3. Подтверждение отмены
4. Система обновляет ВСЕ сообщения в группах
5. Заказ переходит в `cancelled` (конечное состояние)

### Закрытие заказа

**Когда:** Заказ в состоянии `assigned`

**Что происходит:**
- Заказ переходит в состояние `closed`
- Все сообщения в группах обновляются (помечаются как закрытые)
- История сохраняется
- Требуется подтверждение

**Процесс:**
1. Диспетчер выбирает закрытие
2. Подтверждение закрытия
3. Система обновляет ВСЕ сообщения в группах
4. Заказ переходит в `closed` (конечное состояние)

### Общие правила

- Все действия требуют подтверждения
- Все действия обновляют ВСЕ сообщения в группах
- История всех действий неизменяема
- Все действия логируются

## Stage 2.7 — Админ-панель

### Описание
Админ-панель предоставляет полный доступ ко всем данным системы для мониторинга и контроля.

### Доступ

1. **Whitelist админов**
   - Админы определяются по Telegram ID
   - Список хранится в конфигурации
   - Доступ только для админов из whitelist

2. **Полный read-only доступ**
   - Админ видит все данные, но не может изменять
   - Админ не мешает работе диспетчеров
   - Все действия админа логируются

### Что видит админ

1. **Все диспетчеры**
   - Список всех зарегистрированных диспетчеров
   - Статус их сессий
   - Статистика по заказам
   - Активность

2. **Все заказы**
   - Все заказы всех диспетчеров
   - История состояний
   - Детальная информация
   - Фильтры и поиск

3. **Все ответы**
   - Все ответы водителей на все заказы
   - Группировка по заказам
   - Статистика

4. **Все назначения**
   - История всех назначений
   - Смены водителей
   - Причины смен

5. **Все логи и ошибки**
   - Полный доступ к логам системы
   - Фильтрация по уровням
   - Поиск по логам

### Получение ошибок

- **Все ошибки** автоматически отправляются админу
- Уровни: warning, error, critical
- В реальном времени
- С контекстом и стектрейсами

### Интерфейс админ-панели

- Через Telegram бота
- Команды для навигации
- Экспорт данных (опционально)
- Дашборд со статистикой
